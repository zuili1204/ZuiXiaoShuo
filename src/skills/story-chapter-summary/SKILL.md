# 章节事实纪要

## 流程

1. 只读取本章最终正文；细纲用于定位，不得把未写进正文的计划当事实。
2. 提取实际发生的关键事件，按对后续的重要性排序。
3. 在叙事摘要中写入必要的位置、认知、关系或状态变化，不另造 schema 外字段。
4. 列出实际出场人物，不把只被提及的人物混入。
5. 区分本章新埋设与已回收伏笔；没有则返回空数组。
6. 根据真实章尾写下一章需要兑现的事项，不额外发明新悬念。
7. 只输出合法 JSON，由调用方决定是否写库；工具未成功时不宣称已保存。

## 强制输出契约

必须且只能输出以下 JSON，不要 Markdown 代码块或解释：

```json
{
  "summary": "不超过200字的叙事性本章摘要",
  "keyEvents": ["实际关键事件1", "实际关键事件2"],
  "charactersInvolved": ["实际出场角色1", "实际出场角色2"],
  "newForeshadowings": ["本章新埋设的伏笔"],
  "resolvedForeshadowings": ["本章实际回收的伏笔"],
  "nextChapterHook": "章尾已经存在、下一章需要处理的具体事项"
}
```

## 字段约束

- `summary`：概括“谁做了什么、结果如何、状态怎样变化”，不是条目拼接。
- `keyEvents`：只写会影响后续的事件，通常 2—5 条，不为了凑数拆碎同一动作。
- `charactersInvolved`：使用正文与项目人物卡一致的姓名。
- `newForeshadowings`：仅记录读者已能观察到、未来需要回证的内容。
- `resolvedForeshadowings`：必须确实回收，不把部分推进写成完成。
- `nextChapterHook`：没有明显悬念时写已形成的下一步任务或决定，不强行制造事故。

## 禁止

- 不写质量评分、修改建议、写作分析和市场评价。
- 不把细纲中漏写的事件补进纪要。
- 不在 JSON 外添加“以下是摘要”等文字。
